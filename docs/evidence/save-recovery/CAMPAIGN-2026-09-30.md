# Campaign evidence — save recovery from a missing primary (F-01)

**Change:** `recover-save-from-backup-when-primary-is-missing`
**Findings closed:** F-01 (P0, total save loss) and F-10 (boot outcome taxonomy)
**Decision:** `docs/DECISIONS.md` D-052
**Baseline:** `df68574` (295 tests green)
**Executed:** maintainer's Windows workstation via Git Bash, .NET SDK 9.0.300

## 1. Severity

Recorded as **Critical / P0** in the master plan's findings register. A single
`rm save.json` between the store's own delete and move steps destroys a player's
entire world, with no error and no recovery. The flagship product invariant is
"progress is never silently destroyed".

## 2. The defect, reproduced with the committed CLI (BEFORE the fix)

```text
$ T=$(mktemp -d)
$ dotnet run --project tools/simulation -- walk --save "$T" --days 8 \
      --steps-per-day 12000 --at 2026-08-20T08:00:00Z
# 8 days of world progress committed
$ ls "$T"
save.backup.json   save.json

$ rm "$T/save.json"        # the exact Delete/Move window AtomicFileSaveStore.ReplaceFile documents

$ dotnet run --project tools/simulation -- dump --save "$T"
ERROR: no save found (run 'new' first).        # <-- backup never read; 8-day world orphaned

$ dotnet run --project tools/simulation -- walk --save "$T" --days 2 \
      --steps-per-day 12000 --at 2026-08-28T08:00:00Z
[dev] started fresh game seed=42               # <-- total loss
```

The healthy backup generation was sitting in the same directory, readable, at
every one of those steps.

## 3. After the fix — same scenario

Using a 20-day world so progress is measurable:

| Measurement | Before fix | After fix |
|---|---|---|
| `dump` after `rm save.json` | `ERROR: no save found (run 'new' first).` | `WARN: latest primary save was missing; recovered from backup.` + full world |
| `walk` after `rm save.json` | `[dev] started fresh game seed=42` | `WARN: ...recovered from backup.`, `windows: 2 vitality credited: 400` |
| completed projects + landmarks after | 0 (fresh world) | **6** (preserved) |
| Materials after | 0 | **40** (preserved) |

Only the 2 genuinely new days were credited. The 20 days that already existed
were neither lost nor double-credited.

## 4. Root cause

`AtomicFileSaveStore.ReplaceFile` promotes a generation with a delete-then-move
pair (`netstandard2.1` has no `File.Move(overwrite)`). Its own comment says:

> a crash between the two steps leaves the previous generation in backup

So an **absent primary is a reachable state**, not a hypothetical. The boot flow's
first statement after reading the primary was an early return on
`SaveReadOutcome.NotFound`, and `SafeReadBackup()` was never reached on that path.
The store distinguished "absent" from "present but inaccessible" precisely so that
"no save found" would mean the save really is not there — the caller discarded that
distinction.

**The deeper lesson, recorded because it generalises:** the store's mitigation was
already correct. `WriteAtomicPreservingBackup` (D-040) protects the last healthy
generation perfectly — on a code path no caller took. `PersistenceFaultInjectionTests`
already reproduced the exact on-disk state (primary deleted, stale temp, healthy
backup) at the **store** layer; the **application** layer had no test for it. A
mitigation existing is not a mitigation being exercised.

## 7. The two updated tests — and why

`MatureSaveMigrationTests.UnknownProjectRuntime_InPayload_FailsClosed` and
`UnknownDiscoveryRuntime_InPayload_FailsClosedWithoutRewrite` both inject a content
id the authored region does not define. Those payloads **decode cleanly** and then
fail `GameStateValidator`. They asserted `SaveUnreadable`, which is the
misclassification this change removes: the CLI returned exit 3 ("save
missing/unreadable") for what is a data-integrity failure.

They now assert `StartStatus.StateInvalid`. The load-bearing properties are
unchanged and still asserted: boot fails closed, a non-empty detail is produced,
and the damaged generation's bytes are **untouched** on disk.

This is a deliberate behaviour change, called out in the change's design
("`StateInvalid` is genuinely a distinct and useful class — 'the file is fine, the
contents are not'"), and it is the change that makes `StartStatus.StateInvalid`
reachable at all.

  a write-ahead journal recorded as **deferred**, not as open mitigations.
- `docs/DECISIONS.md` **D-052**.

## 10. Not done, deliberately

- **No store write-sequence change**, no second backup generation, no write-ahead
  journal. Those reduce the probability of the state; this change makes the state
  recoverable. Recorded in the master plan's deferred list.
- **No save schema, envelope framing, checksum, or migration change.** Rollback is a
  plain revert; nothing written by the fixed build needs interpretation by the
  previous build.
- **Boot evidence is not persisted** into `GameState`: a second write during a
  recovering boot is the wrong trade, and no other session would read it.
