# Campaign evidence — trusted-time activity acceptance window (F-02, F-03, F-09)

**Change:** `anchor-activity-acceptance-window-to-trusted-time`
**Findings closed:** F-02 (P0, total activity loss on return), F-03 (P1, fast clock
disables crediting), F-09 (P2, deletion markers bypass validation)
**Decision:** `docs/DECISIONS.md` D-053 (supersedes D-030's constants and reference point)
**Baseline:** `b4bca84` (303 tests green)
**Executed:** maintainer's Windows workstation via Git Bash, .NET SDK 9.0.300

## 1. The defect

`ActivityValidationPolicy` compared record timestamps against the **raw device clock**:

```csharp
if (record.EndUtc > nowUtc + MaxFutureSkew)          return FutureTimestamp;  // 10 minutes
if (record.EndUtc < nowUtc - ReconciliationHorizon)  return OutsideHorizon;  // 14 days
```

Two consequences, both in the situations the product is explicitly built for:

1. **A returning player lost everything (F-02).** A player returning after a holiday has
   a provider backlog that is entirely older than 14 days. Every record in it is rejected.
   The activity that earned the most goodwill silently disappears — in direct
   contradiction of the offline-first thesis (D-003/D-004) that the 14-day bound was
   introduced to protect.
2. **A fast clock stopped crediting entirely (F-03).** A device clock running even
   *minutes* fast (routine on phones that resynchronise late) made every record look
   future-dated. Crediting stopped, with no player-visible explanation. `GAME_SYSTEMS.md`
   §15 already required not to rely solely on device wall clock.

And a third, compounding both (F-09): in `IngestActivityBatch` the `if (record.IsDeletion)`
branch preceded `Validate` entirely, so a deletion marker bypassed every eligibility rule
**and** `ProcessDeletion` advanced `maxTrustedEndUtc` from its unvalidated `EndUtc`.

## 2. Why no test caught it

`M5H1ShellAcceptanceTests.Scenario05_ThirtyDayReturn_BoundedCalmLongAbsence` returns after
30 days — but **deliberately ingests nothing during the absence**. So the single most
important ingest scenario for an offline-first game, "the provider hands back the whole
backlog on return", had **zero coverage in the entire suite**.

`SessionIngestionTests.RecordBeyondReconciliationHorizon_IsRejectedWithoutSideEffects`
*did* pin the behaviour — it asserted a 15-day-old record was rejected. The test was
correct about the code and completely blind to the product consequence.

## 3. The fix

| Bound | Value |
|---|---|
| lower | `min(watermark, latest trusted end)` − `TrustedWindowFloor` (45 days); falls back to `now` when a profile has no trusted progress |
| upper | `max(now, watermark, latest trusted end)` + `MaxFutureSkew` (10 minutes) |

The window is computed **once per batch** as a `TrustedTime` value and threaded through
every record, keeping `Validate` `static`, pure and **O(1) per record** with no dependency
on `GameState`.

The 45-day floor bounds how far *before* the last trusted end we still believe a record. It
does **not** bound absence length: records after the last trusted end are inside the window
however far back that trusted end is, which is what makes a 30- or 45-day absence
creditable.

## 6. A real bug the new tests found

`DateTimeOffset` arithmetic is **not** saturating: `DateTimeOffset.MinValue − 45 days`
throws `ArgumentOutOfRangeException`. The first implementation clamped the *result* of the
subtraction, which is too late — the throw happens inside the subtraction. `TrustedTime`
now guards both operations against the distance available to the representable limit, so a
profile whose trusted progress sits at the minimum degrades to "reject everything" rather
than throwing during validation. Caught by
`TrustedTime_ClampsInsteadOfThrowing_NearTheRepresentableMinimum`, not by inspection.

## 7. A recorded divergence from the change's own design

`design.md` and task 4.2 suggested a deletion marker with an **empty provider namespace**
would remain an "ignored" *policy* outcome. The change's **spec** says a marker with "a
missing provider namespace" is "rejected under the corresponding eligibility reason".

The spec is normative, so the spec was followed and the divergence is recorded in
`tasks.md` and D-053 rather than applied silently. Both classifications are equally safe
(neither reverses value nor moves the watermark) and the spec's is strictly more
informative.

A second, larger consequence of the same requirement: **a deletion marker skips exactly one
eligibility rule — the quantity checks.** A marker carries no activity by definition and
every well-formed marker in this repository has `Quantity == 0`. Applying `ZeroQuantity`
would reject every deletion ever issued and silently disable the correction policy. This
was found by the first test run of the restructure, not by inspection. Provenance, unit,
temporal extent and both window bounds still apply to markers.

## 10. Not done, deliberately

- **The watermark does not drive query windows.** It is evidence of how far the pipeline
  has trusted its sources; making it a scheduler is the M7 adapter's job and is recorded
  as deferred.
- **Per-reason rejection counts are still not persisted.** They are produced and returned
  on the immutable result object (and the accounting identity is now asserted in a test),
  but persisting them belongs to `surface-ingestion-rejection-reasons`, which follows this
  change.
- **No conversion, clamp, dedup identity, correction policy or save schema change.**
