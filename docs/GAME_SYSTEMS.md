# Game Systems Specification

## 1. System design objective

Game systems must transform real-world activity into persistent, understandable, and emotionally meaningful world change without creating foreground grind.

Every system should answer four questions:

1. What player behavior feeds it?
2. What canonical state does it own or mutate?
3. What visible consequence does it create?
4. Can the system function correctly while the app is closed?

If a system cannot justify itself against the product thesis, it should not be in the MVP.

---

## 2. Primary resource: Vitality

Vitality is the canonical activity-derived progression resource.

### Requirements

- Generated only from validated eligible activity.
- Credited exactly once through the activity ledger.
- Never inferred directly from UI state.
- Never regenerated by replaying the same source records.
- Conversion rules must be deterministic and versioned.
- Daily/interval bounds may be used for data-integrity and safety reasons.
- Historical conversion rule changes require a documented migration/reconciliation policy.

### Design role

Vitality should primarily represent **restorative capacity**, not generic money.

It can:

- advance projects;
- unlock restoration phases;
- power expeditions;
- accelerate ecological recovery within bounded rules;
- trigger discovery opportunities.

It should not become a universal currency for every system.

---

## 3. Project system

Projects are the primary unit of world transformation.

### Project schema

Each project should have:

- stable project ID;
- region ID;
- title and description keys;
- category;
- prerequisites;
- unlock conditions;
- Vitality requirement;
- optional secondary-resource requirements;
- progress state;
- completion state;
- optional stages;
- canonical world effects;
- optional producer effects;
- discovery/unlock effects;
- presentation references;
- content version.

### Project states

Minimum state machine:

`Locked → Available → Queued → Active → Completed`

Optional `Paused` is allowed if required by queue behavior. Failure should be represented as an operation failure, not a permanent project state unless a specific game mechanic requires it.

### Queue behavior

The project queue must:

- have deterministic ordering;
- define how activity is distributed;
- define behavior when a project completes mid-credit;
- automatically roll remaining eligible progress into the next project when configured;
- avoid wasting activity because the user did not reopen the app;
- expose clear pause/reorder semantics;
- persist atomically.

The default behavior should favor continuity over requiring manual confirmation after every project.

---

## 4. Restoration stage system

A region is represented by canonical restoration state independent of visuals.

Each major landmark should support explicit stages such as:

`Ruined → Stabilized → Functional → Restored → Flourishing`

Not every landmark needs all five stages, but content must define its progression explicitly.

### Stage effects

A stage transition may change:

- mesh/structure state;
- terrain treatment;
- decals/debris;
- vegetation density/type;
- water state;
- lighting/atmosphere;
- ambient population;
- wildlife;
- interactable availability;
- production capability;
- transit/route access;
- narrative/discovery availability;
- audio state.

Presentation should derive from canonical state via bindings. Scene object state may not become the source of truth.

---

## 5. Producer system

Producers create secondary resources or capabilities over time.

Examples may include:

- restored waterworks;
- workshops;
- greenhouses;
- research stations;
- salvage operations;
- ecological nurseries.

### Producer requirements

Each producer owns:

- stable producer ID;
- unlock conditions;
- production rate model;
- resource type;
- capacity;
- last simulation checkpoint;
- upgrade level if applicable;
- enabled/disabled state;
- automation policy.

### Offline production

Offline simulation must be deterministic:

`produced = min(capacityRemaining, rate × eligibleElapsedTime)`

Any modifiers must be versioned inputs to the simulation.

### Anti-busywork rule

Players must not need to claim production every few hours to avoid loss. Storage caps may exist, but caps should be generous enough to respect the product's low-attention promise.

---

## 6. Resource model

The MVP should use the smallest resource set capable of supporting meaningful decisions.

### Recommended baseline

- **Vitality** — activity-derived restorative power.
- **Materials** — optional secondary construction resource generated by restored infrastructure.
- **Knowledge** — optional exploration/research resource tied to discoveries and expeditions.

Do not add a resource merely because a conventional city-builder has one.

### Resource invariants

- no negative balances;
- no floating-point authoritative currency where precision matters;
- mutations occur through domain operations;
- balances persist as canonical state;
- transaction reasons should be diagnosable;
- cap behavior must be explicit;
- failed operations may not partially consume resources.

---

## 7. Discovery system

Discoveries provide narrative and collection payoff.

### Discovery types

- wildlife;
- flora;
- artifacts;
- archive fragments;
- survivor/settlement stories;
- environmental phenomena;
- infrastructure history;
- rare finds.

### Discovery lifecycle

`Unavailable → Eligible → Discovered → Reviewed`

“Reviewed” is a UI convenience state and must not gate core progression unless explicitly documented.

### Trigger models

A discovery may be triggered by:

- restoration milestone;
- cumulative validated activity;
- expedition completion;
- region stage;
- deterministic seeded roll after an eligible threshold;
- optional world visit interaction.

If a discovery can occur through Visit World, equivalent core progression must not require precise exploration input unless it is intentionally optional content.

---

## 8. Expedition system

Expeditions are asynchronous objectives that create anticipation without forcing screen time.

### Expedition schema

- expedition ID;
- region/route;
- unlock conditions;
- required inputs;
- duration or progress target;
- deterministic seed if randomness is used;
- start checkpoint;
- completion condition;
- reward table;
- discovered content possibilities;
- result state.

### Requirements

- continues while app is closed;
- no penalty for returning late;
- result is persisted before presentation;
- retry/replay cannot duplicate rewards;
- randomness, if used, must be deterministic from stored seed/state;
- expedition cancellation rules must be explicit.

---

## 9. Region progression

A region is the highest-level content progression unit.

### Region state

The canonical region should track:

- region ID/version;
- restoration score or milestone state;
- project completion set;
- landmark states;
- unlocked routes;
- ecological state;
- settlement state;
- discovered content;
- producer state;
- expedition availability;
- region completion milestone;
- post-completion state.

### Region completion

Region completion should represent a dramatic transformation, not merely filling an arbitrary bar.

It should require completion of several major chains and result in:

- visual transformation;
- narrative closure;
- sustainable/evergreen systems;
- a strong milestone reward;
- a clean future hook for expansion.

---

## 10. Ecosystem recovery

Ecological recovery is a long-form ambient system that reinforces restoration.

Possible dimensions:

- soil condition;
- water quality;
- vegetation diversity;
- wildlife return;
- pollution/debris reduction;
- habitat connectivity.

The MVP should not simulate ecology at excessive granularity. Use a small number of canonical variables or stages that produce understandable consequences.

The player should be able to see ecological recovery without reading a spreadsheet.

---

## 11. Return summary system

The return summary is a first-class game system.

### Inputs

- time since last meaningful session;
- processed activity;
- Vitality credited;
- projects advanced/completed;
- producer outputs;
- expeditions resolved;
- discoveries unlocked;
- region stage changes;
- automation changes/blocks.

### Output policy

Prioritize:

1. major transformation;
2. actionable decision;
3. noteworthy discovery;
4. concise aggregate numbers.

Do not present every simulation tick.

### Example summary hierarchy

- “The river intake is restored.”
- “East Wetland is now available.”
- “2,430 eligible steps advanced your active project.”
- “Workshop storage is 72% full.”

---

## 12. Automation system

Automation is a core feature, not an accessibility afterthought.

### MVP automation options

- auto-advance to next queued project;
- auto-allocate secondary resources to active project within rules;
- keep one expedition slot working if eligible;
- optional producer overflow conversion if introduced later.

Automation should be understandable, reversible, and deterministic.

---

## 13. Progress pacing

Pacing should be content-driven and testable.

### Pacing goals

- meaningful feedback after ordinary daily movement;
- frequent small changes early without trivializing major restoration;
- visible multi-day project goals;
- region completion over sustained engagement, not a weekend binge;
- no requirement to hit a perfect daily target.

### Simulation testing

Before balancing content manually, the project should include deterministic simulation profiles such as:

- low activity;
- moderate activity;
- high activity;
- irregular activity;
- weekend-heavy activity;
- multi-day inactivity;
- extreme/pathological source values.

Balance should be evaluated across weeks of simulated play.

---

## 14. Randomness policy

Randomness may add surprise but cannot compromise determinism or trust.

Rules:

- canonical random decisions use stored seeds;
- save/reload does not reroll outcomes;
- retries do not duplicate rewards;
- critical progression does not depend on unbounded low-probability drops;
- random discovery systems use pity/threshold logic if required to prevent pathological droughts;
- randomness is never generated in rendering code for canonical outcomes.

---

## 15. Time model

All time-dependent systems must use a shared clock abstraction.

Requirements:

- store canonical timestamps in UTC where practical;
- separate wall-clock display from simulation time;
- handle time-zone changes;
- handle backward clock movement defensively;
- avoid relying solely on device wall-clock for anti-abuse guarantees;
- make simulation checkpoints explicit;
- cap suspicious elapsed intervals where needed;
- test DST, reboot, long absence, manual clock changes, and leap-day boundaries.

---

## 16. Idempotency requirements

The following operations must be idempotent or protected by durable operation identity:

- activity crediting;
- project completion reward application;
- expedition result application;
- discovery grant;
- migration;
- return-summary generation if it modifies reviewed state;
- producer checkpoint advancement.

Replay after crash must not multiply rewards.

---

## 17. Difficulty and challenge

The MVP should not use failure-heavy challenge as its primary retention mechanic.

Challenge comes from:

- choosing restoration priorities;
- deciding resource allocation;
- selecting expedition objectives;
- optional optimization;
- completing collections;
- long-term transformation goals.

A busy player should not be punished for lacking twitch skill or foreground time.

---

## 18. System-level definition of done

A system is complete only when it has:

- documented state model;
- invariants;
- deterministic domain operations;
- persistence representation;
- migration implications;
- offline behavior;
- duplicate/retry behavior;
- error behavior;
- automated tests;
- presentation binding;
- diagnostics;
- acceptance evidence.

No major game system should exist only as scene scripts and UI callbacks.
